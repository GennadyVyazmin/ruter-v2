# Исправление жизненного цикла маршрутизации

## Причина

Старый `route.sh` считал наличие `/var/lib/ruter-v2/route.state` доказательством
активности. После аварийной перезагрузки файл оставался, а состояние ядра Linux
исчезало. Повторный запуск блокировался. Обратная ошибка: без файла stop не
убирал реально существующие правила. `route flush table 220` мог затронуть
чужие записи. CLI проверял лишь статус systemd, а не маршруты.

Старые Requires/BindsTo останавливали маршрутизацию при падении ядра, не создавая
надёжной цепочки её повторного запуска. Отдельного обновления кода не было.

## Новая логика

- Сохраняются таблица 220, приоритеты 12200/12210, интерфейс ruter-v2-tun,
  сеть, IP, ядро и принцип маршрутизации. Основной маршрут хоста не меняется.
- `route.sh` — совместимый wrapper над `ruter_v2/routing.py`.
- Источник истины — JSON `ip rule/route/link/addr` и `ip_forward`.
  Новый runtime `/run/ruter-v2-route/state.json` содержит boot ID, параметры сети
  и исходное значение forwarding; он не является флагом «запущено».
- Повторный start идемпотентен. Недостающие собственные ресурсы добавляются.
  Чужие ресурсы в зарезервированной таблице/приоритетах блокируют изменения.
- Новые ресурсы помечаются protocol 242. Старые точные селекторы принимаются
  только при наличии валидного старого маркера; произвольный чужой ресурс не
  признаётся собственным по одному лишь номеру таблицы/приоритета.
- Миграция старых активных маршрутов не перезаписывает их. Старое сохранённое
  значение forwarding не используется для восстановления после перезагрузки.
  Если его происхождение неизвестно, stop не угадывает значение и оставляет
  forwarding включённым.
- Остановка удаляет отдельные точные собственные записи, начиная с LAN-rule;
  `flush` и удаление только по приоритету отсутствуют. Ошибка применения
  откатывает только добавленные данной попыткой ресурсы, сохраняя прежние.
- Межпроцессный flock сериализует start/stop/status/watch и обновление кода.
- Служба маршрутов — наблюдатель с проверкой раз в 2 секунды. Ждёт TUN, LAN-IP
  и основной маршрут; при исчезновении готовности убирает только свои правила,
  затем восстанавливает их при возврате интерфейсов. Это не kill switch:
  как и раньше, после удаления policy rules может действовать обычный шлюз LAN.
- Ядро тянет службу маршрутов через Wants; PartOf связывает явный stop/restart.
  ExecStopPost убирает ресурсы даже при аварийном завершении наблюдателя.
- CLI отдельно показывает состояние systemd и реальную конфигурацию Linux:
  работает / остановлено / частично / конфликт / ошибка проверки.

## Установка и обновление

Новая установка включает автозапуск, но не запускает службы немедленно.
Пункт 4 запускает шлюз; пункт 8 управляет автозапуском, 9 обновляет программу
из GitHub, 10 удаляет. Первые три пункта не изменились.

Обновление кода не меняет конфиг, подписку, порты, секрет существующей установки,
бинарник ядра, MetaCubeXD и выбранный пользователем автозапуск. Нет `restart`,
`stop`, `enable --now` или пересоздания конфигурации. Кандидат скачивается в
закрытую staging-папку, проверяется тестами и bash, текущий конфиг проверяется
установленным ядром. Файлы заменяются атомарно с резервной копией и откатом
при обычной ошибке. Прерывание питания в середине многофайловой замены требует
повторного запуска bootstrap; резервная копия кода остаётся на диске.

### Безопасный переход существующего шлюза

1. Сохранить снимок ВМ, особенно если доступ только через сам VPN.
2. Старой установке без пункта 9 дать новую команду bootstrap из README.
   Он обнаружит установленный Ruter и обновит код, а не запустит переустановку.
   В новых версиях достаточно `ruter self-update` / пункта 9.
3. Открыть `ruter` заново, проверить пункт 6. Работающие потоки не прерываются.
   Старый oneshot остаётся загруженным до следующего запуска службы.
4. Если прежний автозапуск был выключен, включить пунктом 8. Обновление уважает
   существующий выбор; «по умолчанию включён» относится к новой установке.
5. Для восстановления уже сломанной маршрутизации выбрать пункт 4 или `ruter start`:
   он проверит ядро, применит идемпотентное восстановление и подтвердит Linux-state.
6. В согласованное окно перезагрузить тестовую ВМ. Следующая загрузка использует
   новые зависимости и наблюдатель. Для включения наблюдателя без перезагрузки
   потребуется явный restart только службы маршрутов; это краткий разрыв LAN VPN,
   его обновлятор намеренно не выполняет автоматически.
7. Проверить автозапуск, реальные rules/routes и связь клиентов.

Резервные копии только программных файлов: `/var/lib/ruter-v2/code-*/files.json`.
Не восстанавливайте код старой версии во время работы нового наблюдателя:
сначала согласуйте остановку службы маршрутизации. Старый алгоритм снова
содержит исходную ошибку; предпочтителен повтор безопасного обновления.

## Воспроизводимые проверки

`PYTHONPATH=. python3 -m unittest discover -s tests -v` покрывает модель ядра,
устаревший маркер/смену boot ID, повтор start/stop, потерю TUN, partial apply,
ошибку каждого шага и откат, чужие записи/селекторы, дубликаты, отсутствие
state и сохранность конфигурации при обновлении/откате файлов.

GitHub Actions запускает реальную маршрутизацию только в отдельном namespace:
`sudo unshare --net python3 tests/linux_routing_scenario.py`. Сценарий отказывается
работать в namespace PID 1. Dummy-интерфейсы заменяют VPN — это проверка ядра Linux,
не VLESS и не фактическое выключение питания.

Дополнительный CI-сценарий `tests/systemd_scenario.sh` запускает настоящий systemd
в одноразовом привилегированном контейнере GitHub runner. Тестовое ядро держит
настоящий непостоянный TUN без VPN-учётных данных. Проверяются SIGKILL ядра,
SIGKILL наблюдателя, явный stop/start и аварийное завершение/повторный запуск
контейнера с сохранённым старым маркером и включённым автозапуском.
Это не заменяет проверку загрузки полноценной ВМ с реальным sing-box.

### Проверка на отдельной Debian/Ubuntu ВМ

- Чистая установка: автозапуск enabled, службы пока stopped, start → active.
- Обычная перезагрузка: TUN и четыре ресурса восстановлены, клиент имеет интернет.
- Аварийный reset ВМ после start: после загрузки старый маркер не блокирует start.
- `sudo systemctl kill --kill-whom=main -s SIGKILL ruter-v2-core.service`:
  ядро перезапускается, маршрут восстанавливается, после стабилизации пункт 6 active.
- Аналогично завершить main процесса ruter-v2-route.service: restart и восстановление.
- Удалить только собственный rule 12210 с полным селектором: watcher вернёт его.
- С чужой записью в таблице 220 запуск не должен её удалять; диагностика conflict.
- Обновить работающий экземпляр: PID ядра и конфиг/подписка остаются прежними.
- Повторить на Debian 13 и Ubuntu 24.04/26.04. Настоящие reboot/power-loss и
  работа sing-box/VPN подтверждаются только на ВМ, не unit-тестами.
